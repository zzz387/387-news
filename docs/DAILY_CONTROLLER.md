# Автономный контроллер 387 News — 26 октября 2026

## Причины утреннего сбоя

Запуски №63–69 восстанавливали уже готовые восемь статей и 39 фрагментов, но выполняли только write. У принятого ранее номера audit_passed уже был true: write_batch возвращался без действий, а main не запускал публикацию. Поздний запуск №69, назначенный на 03:17 МСК, появился в Actions в 07:47; фактическая стадия началась около 07:48. Он вновь ограничился write. Ручной resume №70 выполнил сборку около 08:00 и публикацию. Таким образом, одной своевременности cron было недостаточно: завершение зависело от отдельной команды publish/resume.

Дополнительно release_queue.py был привязан к 25 октября и артефакту одного старого запуска. Дата write/research выбиралась иначе, чем audit/publish; после пропущенного планирования не было универсального начала нового цикла. Наблюдение в 07:30 только проверяло сайт и не восстанавливало выпуск. Зелёные задания не подтверждали доставку.

## Как принимаются решения

Все автоматические wake-up вызывают одну фазу run. Часовой пояс Europe/Moscow; cron-строка больше не выбирает стадию. До успешной доставки сегодняшнего номера выбирается сегодняшняя дата, включая после полудня. Проверяются репозиторий и публичный HTTPS. После успешной доставки и наступления 12:00 выбирается завтрашний номер; в полночь это становится сегодняшним номером. Явная дата ручного запуска сохраняется. Старые даты и ID артефактов больше не участвуют в ежедневной маршрутизации.

Контроллер восстанавливает существующий формат checkpoint v31/AES-256-GCM и последовательно выбирает планирование, исследование, написание, адресное исправление или аудит. При 8/8 сохраняет состояние и проверяет форму статей, соответствие плану, досье и буквальные цитаты по сохранённым источникам. Затем выполняет финальный аудит, если хватает времени и запросов. Иначе сохраняет READY_FOR_AUDIT. Уже одобренный номер не пишет и не аудирует повторно.

Проверенная временная HTML-сборка выполняется внутри Actions. До 06:00 публичные файлы не создаются. Если готовый номер обрабатывается в 05:54 и остаётся достаточно времени runner, существующий временной шлюз ждёт 06:00. Любой более поздний запуск публикует готовый номер сразу. Время обновляется после долгих стадий: если написание началось до 06:00, а завершилось после, публикация не откладывается из-за времени старта. Уже существующий публичный архив проверяется локально и по HTTPS; при успехе генерация, изменение файлов и номера выпуска не выполняются. При устаревшем сайте запрашивается только деплой текущих финальных файлов.

Состояния в поле pipeline_status: PLANNING, RESEARCHING, WRITING, READY_FOR_AUDIT, AUDIT_IN_PROGRESS, AUDIT_REPAIR, APPROVED, WAITING_FOR_RELEASE_TIME, PUBLISHING, PUBLISHED, BLOCKED, RETRY_PENDING. Старое поле stage сохранено для совместимости. Итоговый технический JSON и GitHub Job Summary содержат дату, статьи/досье/фрагменты, аудит, дневной и текущий расход, следующее действие и предполагаемое следующее окно. PUBLISHING не означает подтверждённую доставку. Отдельное monitor-задание проверяет сегодняшний сайт после подготовки/деплоя; при отсутствии номера после 06:00 оно завершается ошибкой, не отменяя сохранённый checkpoint.

## Защита от циклов и сбоев

Сохранены 24 запроса за запуск, 220 за день UTC, интервал 6 секунд, cooldown и отказ от fallback при 429/503. Retry-After сохраняется и при смене дня UTC. Проверка наличия бюджета не меняет счётчики. Одобренный номер можно публиковать и при исчерпанной Gemini-квоте: новых API-запросов это не требует. У каждого запуска ограничено число переходов, у аудита/правок остаются прежние пределы. На деплой разрешены три зарезервированные попытки для даты выпуска с интервалом не менее 10 минут. Резерв сохраняется до commit/deploy; прерывание не обнуляет его.

Workflow целиком сериализован через 387-news-stage-v31, cancel-in-progress=false; PR и push тестовой ветки используют отдельные CI-группы без Secrets и Gemini. Потеря гонки git push запрещает деплой. Следующий запуск читает новый main и официальный последний checkpoint. Upload failure запрещает commit/deploy. Все закрытые данные остаются в Actions, загружается только ciphertext. Исторические артефакты и выпуски не удаляются; новые private artifacts хранятся 90 дней. Уже опубликованные HTML/JSON/Markdown не переписываются.

## Наблюдение и уведомления

После 06:00 monitor проверяет главную, архив, дату, восемь полных статей и публичный манифест. Различаются неподготовленный номер, готовый неопубликованный номер, устаревший сайт, внешняя ошибка, квота, критический редакционный отказ и предел деплоев. После часового льготного окна либо сразу при критической блокировке создаётся один GitHub Issue с маркером даты. Повторные сбои обновляют этот Issue; успешный HTTPS-контроль закрывает его. В уведомлении только безопасный код и техническая инструкция, без закрытых причин или досье. Если GitHub Issues выключены/недоступны, Summary сообщает notification_error; требуется действие владельца.

GitHub может задержать или пропустить любой cron, точная минута не гарантируется.

Repository Variables остаются прежними: NEWS_AUTOMATION_V31_ENABLED=true и NEWS_RELEASE_APPROVED=true. Существующие ночные scheduled runs и успешный деплой подтверждают их включение. Secrets менять не нужно. daily.yml и daily-v3.yml остаются выведенными из эксплуатации, Gemini probe — ручная диагностика.

Встроенный динамический pages build and deployment всё ещё наблюдался в истории. Подключённая интеграция не управляет настройкой Pages Source. Владелец может окончательно оставить единственный способ доставки: Settings → Pages → Build and deployment → Source → GitHub Actions. Это не заменяется обходом настройки в Python.

## Проверки и границы доказательств

158 тестов прошли локально до CI, включая все 14 сценариев задания, адресный аудит, восстановление ledger после смены дня, остановку runner, публикацию без Gemini, неизменность архива и дедупликацию/закрытие инцидента. Тестовые данные вымышленные, реальные Gemini-запросы в тестах не выполняются. Контроль main должен восстановить реальное существующее состояние внутри Actions и подтвердить текущий публичный номер без его изменения. Сравнение Git blob SHA защищает опубликованные материалы 25–26 октября от изменений техническим PR.

Новый ежедневный цикл за 27 октября нельзя считать проверенным реальной эксплуатацией до его фактической автоматической публикации. При устойчивом недостатке доказательств, редакционной блокировке, истечении артефакта, полном отказе GitHub или исчерпании повторов Pages понадобится владелец. При SIGKILL/утрате runner до успешного upload возможна потеря работы после предыдущего загруженного checkpoint; обещания exactly-once для внешнего API нет. Ни публикация раньше срока, ни снижение редакционных требований не используются для обхода этих ограничений.
