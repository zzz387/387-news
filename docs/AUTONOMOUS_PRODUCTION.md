# Автономная подготовка 387 News 3.2

> Актуальное описание ежедневного запуска: [DAILY_CONTROLLER.md](DAILY_CONTROLLER.md). Исторические шаги восстановления ниже не управляют новыми выпусками.

Владелец разрешил публикацию и ежедневный запуск. Технический шлюз `NEWS_RELEASE_APPROVED` сохраняется; включение Repository Variables выполняет владелец, поскольку подключённая интеграция не поддерживает эти настройки. Редакционные приоритеты 3.2 сохранены: восемь статей, 2–3 больших очерка по 1050–2200 слов, остальные от 440 слов, суммарно от 5000 слов, обязательные жизненные рубрики и проверяемые источники.

## Состояния и восстановление

`plan → research → write → audit → publish` выполняются отдельными заданиями. `write` также исправляет отклонённые фрагменты. Для реальных испытаний временный push-hook тестовой ветки запускал preview-only фазу `auto`; после испытаний этот hook удалён. Pull Request запускает только тесты без секретов/API.

Досье содержит буквальные цитаты, проверенные по загруженным источникам. Извлечение накапливает уже подтверждённые свидетельства между запусками; до трёх попыток получить минимум восемь для большого очерка и пять для короткой статьи. После исчерпания попыток сюжет отклоняется. Большой очерк собирается из 8–10 самостоятельных фрагментов, короткая статья — из 4–6. Один фрагмент получает до трёх попыток за вызов и до девяти после восстановления; диагностика длины, структуры и повторов передаётся следующей попытке. Принятые фрагменты не переписываются. Финальный текст обязательно проходит прежние требования объёма и модельную редакционную проверку, включая заголовок, анонс и основной текст. У ранее сохранённых статей без отметки новой области проверки анонсы проверяются перед аудитом без повторного написания статей. Отклонённый за недостаток доказательств сюжет помечается `rejected`; на следующем write подбирается альтернативный проверенный кандидат того же объёма, по возможности той же рубрики (до трёх замен); обязательные рубрики, разнообразие и лимиты использования источников проверяются повторно. Прочие задания и готовые статьи сохраняются. Если подходящих замен нет, неполный номер не публикуется. Нельзя гарантировать ежедневный выпуск при недостаточной фактической базе.

Каждый принятый фрагмент, досье и черновик перед проверкой атомарно сохраняются локально в AES-256-GCM checkpoint. Ошибка/429/503 во время проверки не удаляет написанную статью. Обычный выход, ошибка и SIGTERM сохраняют состояние. `always()` загружает только ciphertext; отдельный JSON содержит лишь счётчики запросов и время cooldown. Следующий независимый запуск скачивает артефакт с явными artifact ID и source run ID. Ошибки скачивания, дешифрования и метаданных останавливают работу, а не запускают генерацию с нуля.

В фазе auto полный номер также проходит аудит и временную preview-сборку.

Состояние preview отделено от production и от других веток. Контрольный файл старого main в формате версии 31 совместим. Ветка PR получает собственный суффикс имени артефакта. Фаза `check`, preview=true, с той же датой проверяет восстановление без обращений к Gemini.

## Квота и остановка

Пределы workflow: 24 фактических HTTP-запроса за запуск, 180 за сутки UTC, интервал минимум 6 секунд, мягкая остановка через 12 минут с запасом на сохранение. Считаются также неудачные HTTP-запросы, повторные ответы и проверки. Общий дневной ledger восстанавливается независимо от даты выпуска и preview; concurrency сериализует задания. Снимок счётчиков продублирован внутри зашифрованного checkpoint.

429 и 503 приостанавливают весь этап без перехода на другую модель. Cooldown сохраняется, Retry-After учитывается. Фактические лимиты Google могут быть ниже установленных локальных потолков; при необходимости уменьшите их в workflow. Счётчик не видит другие программы, использующие тот же Google-проект. Список моделей не включает подключение биллинга; код не создаёт облачные или платные ресурсы.

При SIGKILL, потере runner или одновременном отказе всех загрузок артефактов может потеряться работа после последнего успешно загруженного checkpoint. Нельзя обещать exactly-once для внешнего API при таком сбое. Не удаляйте артефакты активного выпуска. Срок хранения новых артефактов — 90 дней; это не бессрочный архив. Финальные статьи сохраняются в Git как HTML, Markdown и публичный JSON. Истёкший найденный checkpoint блокирует автоматический сброс. Ошибка upload делает workflow красным и блокирует commit/deploy.

## Безопасная проверка

1. В Actions выберите `387 News — editorial v3.1 (SAFE / manual approval)`, рабочую ветку, `plan`, preview=true, фиксированную дату.
2. Выполните `research`, затем несколько `write` с той же датой, пока в журнале не появится 8/8 проверенных статей. Между write выполняйте `check`. Уже готовые статьи и принятые фрагменты должны сохраняться.
3. Выполните `audit`. Для полного номера проверьте одобрение, затем `publish` с preview=true. Сайт останется без изменений.
4. Все preview-прогоны должны иметь пропущенные commit/deploy. Временный push-hook удалён после заключительной проверки, чтобы будущие коммиты PR не расходовали квоту. Для повторения проверки используйте ручные plan/research/write/check/audit/publish с preview=true и одной фиксированной датой.

Локально: `python -m pip install 'cryptography>=44,<49'`, затем `python -m unittest discover -s scripts -p 'test_*.py' -v`. Тест восстановления использует два отдельных процесса Python, настоящий шифрованный файл и поддельные ответы API; его нельзя выдавать за реальный тест Gemini.

## Включение ежедневного производства

После проверки и слияния PR:

1. Проверьте существующие Secrets `GEMINI_API_KEY` и `DRAFT_ENCRYPTION_KEY` (base64 от 32 случайных байт). Не публикуйте их значения. Не меняйте ключ шифрования, пока нужны старые черновики.
2. Старые `daily.yml` и `daily-v3.yml` выведены из эксплуатации: cron удалён, выполняющие публикацию задания безусловно выключены. Они остаются в списке Actions ради истории; статус Disabled через настройки интеграция установить не может.
3. В Settings → Secrets and variables → Actions → Variables установите `NEWS_AUTOMATION_V31_ENABLED=true` и `NEWS_RELEASE_APPROVED=true`. Разрешение владельца уже получено. Подготовка продолжит существующий production checkpoint.
4. Расписание МСК: план 12:17, исследование 14:17; запись/исправление 16:17, 18:17, 20:17, 22:17, 00:17, 01:17, 03:17, 04:17; аудит 05:17; попытка выпуска 05:54 с ожиданием до 06:00. GitHub cron и Pages не гарантируют точного времени. Резервные окна: запись 06:17, аудит 06:37, публикация 06:54; проверка свежести публичного сайта — 07:30 МСК.
5. `NEWS_RELEASE_APPROVED=true` разрешает публикацию из main после полного аудита и успешных загрузок. Для остановки публикации верните false; для остановки производства выключите NEWS_AUTOMATION_V31_ENABLED.
6. Проверяйте итоговое состояние и 8/8, а не только зелёный workflow: мягкая остановка по квоте сохраняет прогресс и может завершиться успешно без готового номера. Если исчерпаны подтверждённые альтернативы, требуется новый редакционный план/источники; программа не заполняет его выдуманным текстом.

## Граница закрытых данных

Реальные досье и зашифрованные черновики обрабатываются только внутри GitHub Actions, с существующими Secrets и официальными download/upload-artifact. Не скачивайте их для локального аудита и не экспортируйте ключи. Локальные тесты используют исключительно вымышленные данные. Публичный выпуск содержит только финальные статьи и разрешённые поля публичных источников. Pages получает отдельный пакет разрешённых статических каталогов; исходный репозиторий целиком не загружается.

Повтор publish для уже записанного идентичного выпуска повторяет деплой без перезаписи архива. Несовпадение финального содержимого запрещает замену. После деплоя проверяются HTTPS, дата, восемь полных HTML-статей и соответствие публичному манифесту. Ручная фаза status не читает Secrets и черновики.
